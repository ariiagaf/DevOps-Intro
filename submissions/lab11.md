# Lab 11 — Reproducible Builds of QuickNotes with Nix

**Repository:** https://github.com/ariiagaf/DevOps-Intro/tree/feature/lab11

## Task 1 — Reproducible Go Build

The root `flake.nix` pins `nixpkgs` to the `nixos-25.11` input, with the exact revision recorded in committed `flake.lock`. The flake defines `packages.<system>.quicknotes` and `packages.<system>.default` using `buildGoModule`, with `src = ./app`, `env.CGO_ENABLED = "0"`, and `ldflags = [ "-s" "-w" ]`. The development shell provides Go, `gopls`, and `golangci-lint`. Both `aarch64-darwin` and `x86_64-linux` are declared.

QuickNotes built successfully with `nix build .#quicknotes`. Running the binary and requesting `GET /health` returned **HTTP 200 OK** and `{"notes":0,"status":"ok"}`.

Two independent GitHub-hosted Linux runners built QuickNotes with the same locked inputs. The Nix store hashes matched:

```text
build-a: sha256:056fmmb50m76dzacl1syfz07zjaj9hdlvwxnxfdfry25gj4phf6i
build-b: sha256:056fmmb50m76dzacl1syfz07zjaj9hdlvwxnxfdfry25gj4phf6i
```

A local macOS build and a fresh checkout using the same local Nix store also produced the same store hash (`sha256:0lij8b6050lz6mbpzcmh45n1nhfmykvy0azmyb1smwhrj0cqz197`); the independent-runner Linux comparison above is the stronger reproducibility evidence. The macOS and Linux hashes are not expected to match because their target systems differ.

## Task 2 — Deterministic Docker Image

The flake exposes `packages.x86_64-linux.docker` via `pkgs.dockerTools.buildImage`. The image is generated by Nix without a Docker daemon. It contains the QuickNotes executable, uses an exec-form `Entrypoint`, declares `8080/tcp`, and runs as non-root UID/GID `10001:10001`. A writable `/data` working directory was added after an initial `permission denied` error when the application tried to create its data directory.

The resulting image was loaded on a GitHub Actions Linux runner with `docker load < result` and started with `docker run -d -p 8080:8080 quicknotes:nix`. The container health endpoint returned **HTTP 200 OK** and `{"notes":0,"status":"ok"}`.

Two independent Linux CI jobs built `nix build .#docker` and compared SHA-256 values of their output archives. The comparison passed. One measured archive had the following digest and size:

```text
Archive SHA-256: 6a8d6fa8659a23de34480a2e05fe81e35a086e117d71c82ce3c990981f6f0937
Compressed archive: 5.6 MB (du -hL result)
Loaded Nix image: 14,789,202 bytes (~14.8 MB)
```

For comparison, the existing `app/Dockerfile` was built twice with `docker build --no-cache` on the Linux runner:

| Build | Docker image size | Full image ID |
| --- | ---: | --- |
| Dockerfile build 1 | ~14.1 MB | `sha256:cc7436e6a01f0696b0a9ab87575c5a18a101bfccc582a82e828594016e451eec` |
| Dockerfile build 2 | 14,075,212 bytes (~14.1 MB) | `sha256:016ba679259670aeeed9de7257778fadce88fe8a19b7311490f40d5626d6ca8a` |
| Nix image | 14,789,202 bytes (~14.8 MB) | `sha256:7345d208e5bd9891e5bc382f23673c620fc8581d784354d7033eceb8ad4c5342` |

The two conventional Docker builds had different image IDs despite using the same Dockerfile. This demonstrates an image-level difference, not necessarily a difference in application file contents. The compressed Nix archive size and the loaded Docker image size measure different things and should not be compared as equivalent sizes.

**Evidence:** [Container health and Nix image measurements](https://github.com/ariiagaf/DevOps-Intro/actions/runs/38735372745); [Dockerfile comparison](https://github.com/ariiagaf/DevOps-Intro/actions/runs/38735778391).

## Bonus — Reproducibility CI

`.github/workflows/nix-repro.yml` runs on pushes and pull requests. Two parallel, independent Ubuntu runner jobs check out the repository, install Nix using commit-SHA-pinned GitHub Actions, build `.#docker`, and publish archive SHA-256 outputs. A third job compares the two outputs and fails if they differ. The workflow also checks the QuickNotes binary's Nix store hash on both runners.

To demonstrate failure detection, one runner's published hash was temporarily replaced with an intentionally incorrect value. The comparison failed. The original hash calculation was then restored and the workflow passed.

## Design Questions

**a. Why might ordinary `go build` not be bit-for-bit reproducible?** Different Go toolchain versions, dependency versions, build flags, environment settings, embedded paths, and generated metadata can change output bytes. Nix fixes the build inputs and environment more tightly.

**b. What does `vendorHash` protect, and why is it `null` here?** For `buildGoModule`, `vendorHash` pins the hash of the vendored Go module dependency tree, so changed dependencies cannot silently enter the build. This QuickNotes module has no external Go module dependencies, so `vendorHash = null` is appropriate.

**c. Why is `flake.lock` important?** A branch or channel name can move. The lock file records the exact resolved input revision and content hash, allowing future builds to use the same nixpkgs source.

**d. `buildGoModule` versus `buildGoApplication`?** `buildGoModule` is the standard nixpkgs Go-module builder used here, including Nix-managed module dependency handling and caching. `buildGoApplication` is an alternative builder provided by other tooling (not the standard nixpkgs builder in this flake); its implementation and dependency handling depend on that tooling. For this repository, `buildGoModule` integrates directly with pinned nixpkgs.

**e. Why can ordinary Docker builds differ?** Mutable base-image tags, unpinned packages, timestamps, build metadata, network-fetched inputs, and build-environment differences can affect image output. Our two `--no-cache` builds produced different image IDs.

**f. How does a deterministic image help an auditor?** The auditor can rebuild from the declared inputs and compare a cryptographic digest with the published artifact, making unexpected changes easier to detect and investigate.

**g. What are the trade-offs of Nix-based image builds?** Nix improves dependency pinning, reproducibility, and build isolation, but introduces a learning curve, Nix store/cache management, platform-specific builds, and additional maintenance of the flake and lock file.

**h. What does reproducibility CI verify?** It checks whether separate runners using the same locked source and configuration produce identical artifact hashes, and fails if the results diverge.

**i. Why use two independent jobs?** Separate fresh runners reduce the chance that a shared local build result or store cache is mistaken for two independent builds. Both jobs must actually build the same target and report their own hashes.

**j. What is `SOURCE_DATE_EPOCH` for?** It provides a fixed reference timestamp for build tools that honor it, reducing timestamp-based nondeterminism. It does not by itself guarantee reproducibility; all relevant inputs and metadata must also be controlled.
